## Problem Statement

The pay-on-pass agent on `main` works on preprod in both directions (pass → payout, fail → refund in 4.5 min, `docs/evidence.md`). Its weak point is the customer story (`docs/PROGRESS.md`, proposal 2): the current app `eth-vault` gives no clear answer to "who pays and why on Cardano". This design swaps the Cardano demo's app for one with a clear customer, and keeps the escrow machinery.

## What Makes This Cool

A customer hires **one** agent to write code. That agent splits the job and **hires three sub-agents** on Masumi, each with its own escrow. Sub-agents that pass the unit tests get paid. The one that fails gets nothing, and its escrow goes back **live on cardanoscan**. Our agent itself is paid only if the assembled code passes the integration test.

- **Nested escrow:** the risk flows down the chain, and every link is a transaction on preprod.
- **Pitch line:** "On Upwork the arbiter is a human and it takes weeks. Here the arbiter is a test suite: a decision in minutes, an automatic refund, and on-chain proof."
- **10x line:** "Every GitHub issue becomes a job for any agent in the world. CI is the arbiter."

It hits two of the Cardano judges' explicit asks at once: agents that hire other agents, and payment tied to the result.

## Premises (agreed in session)

1. **The originality is the nested escrow, not test-gating itself.** Test-gated escrow for coding agents already exists (AI2Work on Celo, BountyNet at ETHGlobal Cannes 2026, TaskBounty, ArcAgent, OutcomePay AI). None of these was found on Cardano/Masumi in one web search. That search is the limit of the "first on Cardano" claim.
2. **Tests are public and committed on chain.** The test file goes into the job input, and Masumi writes the input hash on chain at purchase. The seller runs the tests and **withholds the result on fail**, which triggers the existing refund path. Anyone can re-run the committed tests against the committed result hash. This premise was revised after the second opinion; the original version ("the buyer holds hidden tests") moved the trust problem to the buyer.
3. **Open:** Julien still has to confirm how much of the existing code carries over. Batu could not judge this, and the second opinion's file-level estimate is below.
4. This replaces `eth-vault` as the **Cardano** demo. The API3 vault stays a separate API3-track submission. **This is a team decision and is not yet confirmed.**

## Cross-Model Perspective (independent Claude subagent, cold read)

- **Coolest unconsidered version:** commit-reveal of *hidden* tests, where the seller re-runs the revealed tests and authorizes the refund only if they really fail. That is Approach B.
- **What excites the team:** "the live refund of the failing sub-agent on cardanoscan". The advice is to build the demo backwards from that frame.
- **50% shortcut:**
  - `cardano-agent/` already has the escrow, the refund guard, proofs and receipts.
  - OpenAI `human-eval` (MIT) provides problems with tests, and small models really fail some of them, so the "weak" agent is not staged.
- **Verified in code (checked again by the main session):**
  - `refunds.py:72` only authorizes payments in state `RefundRequested`.
  - `README.md:108` says a refund requested *after* a delivered result "stays a dispute for a human".
  - So "refund after delivery" is **not** supported today, and Approach A avoids it.
- **Deadline risk:** `masumi_v2.V2Payment` reads its deadlines from one shared `.env` at class level. Child jobs need their own deadlines (about 15 min) nested inside the parent's (about 40 min), so this needs per-process env.
- **Demo timing:** payouts can't settle live. Show the refund live and the payouts from pre-run proofs.

## Approaches Considered

### Approach A: Public tests, seller withholds on fail (CHOSEN)
- The tests are in the job input, so their hash is on chain.
- Each sub-agent writes code, runs the tests and withholds the result on fail, which uses the already-proven refund path.
- The orchestrator is the seller to the customer and the buyer from three sub-agents.
- Effort M, risk low to medium.
- Cons: the tests are visible, so an agent could overfit to them, and the nested deadlines are tight.

### Approach B: Commit-reveal hidden tests + refund after delivery
Rejected for now. It depends on Masumi allowing an automatic refund after a delivered result, which goes to a human dispute today and is untested on preprod. It could become a stretch goal if one test job tonight shows otherwise.

### Approach C: Tryouts (same job to three agents, first pass wins)
Rejected. It is the closest to TaskBounty and loses the nested-escrow story.

## Recommended Approach

**A.** It reuses the refund path that is already proven on preprod, it fits the freeze, and it keeps the nested-escrow originality.
